# 核心思路（SFW / NSFW 共用）

> 生成时间：2026-11-10
> 性质：**不是规则抄录，是本项目的设计总纲**
> 配套：各分册（[H3提示词规则.md](./h3-prompt-rules.md)、[分镜系统规则.md](./storyboard-rules.md)、[素材与配置规范.md](./assets-and-config.md)、[NSFW模式设计.md](./nsfw-design.md)）
> **本文件回答一个问题：这个软件到底在做什么、靠什么保证它做得好。**

---

## 〇、一句话

> **输入一份文本，产出一套能让 AI 生成连贯短剧的镜头化指令。**

模型是别人训的，画面是模型画的。**我们唯一的产出是「指令」，唯一的护城河是指令的可靠度。**

所以这个软件的本质不是"AI 视频工具"，是**「从文本到可靠指令的编译器」**。

---

## 一、三层模型：事实、计划、渲染

整个系统只有三样东西，从上到下单向流动。

```
┌──────────────────────────────────────────────┐
│  ① 事实层（CF · Canonical Facts）             │
│     世界 / 场景 / 人物 / 道具                  │
│     每条带证据等级：原文 / 推断 / 补全 / 待确认  │
│     ★ 唯一事实源，全局只有一份                  │
└─────────────────────┬────────────────────────┘
                      │ 只读
                      ▼
┌──────────────────────────────────────────────┐
│  ② 计划层（CSP · Canonical Shot Plan）        │
│     段落 SEG[] → 镜头 SHOT[]                  │
│     时长级联 / 台词预算 / 动作槽 / 连续性        │
│     ★ 与模型无关，只和内容有关                  │
└─────────────────────┬────────────────────────┘
                      │ 只读 + 策略注入
                      ▼
┌──────────────────────────────────────────────┐
│  ③ 渲染层（Adapter）                          │
│     内容策略：SFW | NSFW                      │
│     目标模型：H3 六段 / 三字段 / 四模块…        │
│     ★ 纯投影，不改内容                          │
└──────────────────────────────────────────────┘
```

### 三条铁律

**① 单向流动**

事实层 → 计划层 → 渲染层，**绝不反向**。

渲染层发现的问题，只能修改上游再重跑，**不能在渲染层打补丁**。这是唯一能保证「同一份计划渲染出不同模型提示词，内容仍然一致」的方式。

**② 唯一事实源**

每个对象在整个项目里**只有一处定义**，其他地方只引用编号。

改人物设定 → 改 CF → 重跑依赖它的所有镜头。不在镜头里重新描述人物。

**③ 渲染是投影**

适配器（Adapter）**只做翻译，不改内容**。

H3 六段壳和 MiniMax 四模块，描述的是同一件事，只是语言不同。如果两个模型出来的内容不一样，那是 bug。

## 二、四条底线

这四条不是"最佳实践"，是**不满足就是错的**。

### 底线 1 · 事实铁律：可补美术，不可补剧情

> **证据优先级：原文 ＞ 原文直接推断 ＞ 合理美术补全。**
>
> 可补材质、光影、陈设、服装细节；
> **不可补人物关系、情节、动机、结局。**

没证据的关键事实 → 标 `【待确认】`，不许编。

**为什么**：用户给的是他的故事。我们编一句台词，就是毁他的作品。

**怎么守**：每条事实带 `EVID`。交付前统计「待确认」数量，让用户自己看。

---

### 底线 2 · 台词是定数，镜头数是变数

> **剧本里每一句台词，都必须能在某一条提示词里找到。**
>
> 装不下 → **加时长或拆条**，绝不删台词、不并句、不概括。

**这是本鲸读完全部资料后，认为全项目最重要的一条。**

因为它是唯一一条**方向性错误** —— 几乎所有人的第一反应都是"这个镜头塞不下，删两句"，而正确方向是"多给一个镜头"。

**换算**：H3 一条 15 秒最多 3–4 句台词。某段有 N 句 ⇒ 至少 `ceil(N / 3)` 条。

**为什么**：台词是剧情的载体。删台词就是删剧情，这是底线 1 的直接推论。

---

### 底线 3 · 从事实重建，不从渲染结果推断

> 每个镜头开头，**从事实层重建「第 0 秒一切的位置」**，
> **不沿用上一个镜头的渲染画面去推断。**

**为什么**：误差会复合放大。

第 2 条从第 1 条的画面推空间 → 第 3 条从第 2 条推 → 第 10 条已经完全跑偏。**接帧链最大的风险不是接不上，是越接越歪。**

**注意**：接帧用的尾帧**只提供像素**，不提供位置信息。位置永远从文本事实来。

---

### 底线 4 · 不完整不出片

> 任一质量门不过 → **停止下游，显式标注缺口与影响**。
>
> **禁止静默降级，禁止宣称完成。**

要明确列出：未完成项 + 原因 + 对成片的影响 + 建议（补素材 / 换模型 / 改时长）。

**为什么**：这个软件的用户是要拿成品去发布的。「差不多能看」和「能用」之间差着一整个返工周期。**宁可告诉他哪里不行，也不要给他一个看起来行的东西。**

## 三、内容策略：一层，不是两条流水线

SFW 和 NSFW **共用全部管线**，只在渲染层分叉。

```
事实层  ──┐
计划层  ──┼── 完全共用
质量门  ──┤
渲染层  ──┴── 策略注入点
              ├─ policy-sfw
              └─ policy-nsfw
```

### 3.1 什么共用、什么不共用

| 组件 | SFW | NSFW |
|---|---|---|
| 事实层 / 计划层 | ✅ 共用 | ✅ 共用 |
| 时长级联、台词预算、动作槽 | ✅ 共用 | ✅ 共用 |
| 资产编号 | ✅ 共用 | ✅ 共用 |
| 模型适配器（六段壳/三字段/四模块） | ✅ 共用 | ✅ 共用 |
| 质量门（风险分、因果审计） | ✅ 共用 | ✅ 共用 |
| **动作/表演描述库** | 通用描述 | 8 类动作库 |
| **程度控制** | 无 | L0–L5 档位 |
| **模块选择** | 无 | M1–M5 |
| **躯体状态** | 无 | 7 维 × 5 档梯度 |
| **术语** | 通用 | 解剖术语 + 禁用代称 |
| **负面词** | ①②③⑤⑥ | ①②③④⑤⑥ |
| **合规闸门** | 通用 | **成年主体判定** |

**比例：约 85% 共用，15% 分叉。**

### 3.2 分叉的实现方式

**不用两份完整文档，用「骨架 + 片段」拼装**：

```
prompt = base.md + policy-{sfw|nsfw}.md
```

这样：
- 改运镜规则 → 只改 `base.md`，两边都生效
- 改动作库 → 只改 `policy-nsfw.md`
- 不会出现「SFW 版修了 bug，NSFW 版没修」

**唯一必须分开的是合规闸门** —— 它不能是策略参数，必须是硬编码的拦截。

### 3.3 分叉粒度

`Shot` 级别挂 `contentPolicy`，不是项目级。

**原因**：一个剧可能大部分是 SFW，只有几场是 NSFW。项目级开关太粗，会导致整部片子被标记。

## 四、多入口，单管线

### 4.1 三个入口，同一种产物

```
入口 A  导入 TXT / 小说   ──┐
入口 B  粘贴文本          ──┼──→ 一份文本 ──→ 同一条管线
入口 C  Agent 对话生稿     ──┘
```

**关键认知：入口 C 产出的「成稿」，和入口 A 导入的 TXT，是同一种东西。**

这不是三个功能，是**同一条流水线的三种喂料方式**。

### 4.2 入口 C 的做法（借鉴 TK 写作 SKILL）

Agent 对话生稿走**五阶段**：

```
阶段一  需求澄清与初始化   逐一提问，不一次抛完；建知识库
   ↓
阶段二  大纲细化与章节规划  写进知识库
   ↓
阶段三  逻辑优先的初稿     正常叙事，尺度场景留 [占位符]
   ↓
阶段四  尺度场景专项实现   逐个占位符填，先交互确认需求
   ↓
阶段五  整体润色与一致性    对照知识库校验
```

**阶段三的「占位符留白」是本鲸认为这套方法最妙的地方。**

> 遇到尺度场景时，**严禁直接编写细节**，用 `[NSFW: 场景描述]` 占位。

**为什么妙**：它把「写剧情」和「写尺度」彻底分开。先保证故事连贯可信，再一个个填。**和「先规划 CSP 再渲染」是同一个思路，只是用在写作层。**

### 4.3 对话期间不落盘

> **对话进行中不生成任何半成品文件。** 成稿是「对话确认结束之后」的事。

**为什么**：中间状态一旦落盘，就可能被误当成定稿。宁可只在内存里，也不要留个半截文件在磁盘上。

## 五、质量门：三道闸

### 5.1 闸一 · 输入闸

- 素材齐不齐（按分支给清单，缺必须项就直接说做不了）
- 合规判定（NSFW 模式下必过）
- 文本能不能切出足够的场景/人物/道具

### 5.2 闸二 · 计划闸

计划层出完，先自检再渲染：

| 检查 | 标准 |
|---|---|
| 时长闭合 | 时间码连续、无缺口、`end − start = D` |
| 台词预算 | `字数 ≤ floor(D × 2.5)` |
| 动作密度 | `槽数 ≤ min(9, round(D × 0.6))` |
| 台词覆盖 | **剧本每句台词都能找到落点** |
| 连续性 | 每镜从事实重建初始位置 |
| 资产引用 | 编号唯一、引用存在 |

### 5.3 闸三 · 渲染闸

- 结构正确（段数、字段名、顺序）
- 枚举值合法
- 编号契约（关键帧不占 `<Picture N>`）
- 禁写清单（无「停留/定格」等）
- 字节干净（无孤立 CR、无伪行）

### 5.4 打分与修复

**20 项风险分**（0 安全 / 1 关注 / 2 高风险），**任一 2 分不许出片**。

修复必须：**重跑受影响的全部下游，不是只改出错处**。

改一个时长 → 时间码、台词预算、动作槽、子镜切分全部重算。**这就是「级联」的含义。**

#### 5.4.1 闸与 20 项的映射（2026-11-10 补）

> 之前三层闸和 20 项风险分是两套东西，没接上。这里接上：**每一闸只跑自己那几项**，
> 不是每闸都跑 20 项——那会让闸一替闸三背锅，也让失败原因看不出来。

20 项在 `分镜系统规则.md` §8.1 里本来就有分组，正好对上三道闸：

| 闸 | 对应风险项 | 项数 | 何时跑 | 不过怎么办 |
|---|---|---|---|---|
| **闸一 · 输入闸** | ① 证据缺口<br>② 矛盾未裁决<br>③ 主体遗漏/多抽<br>④ 状态变体缺失<br>⑤ 时间线断裂 | **5**（Phase A 全组） | 读完文本、还没出计划 | 停下来问，不猜 |
| **闸二 · 计划闸** | ⑥ 时间码不闭合<br>⑦ 初始位置未从事实重建<br>⑧ 动作超 9 槽<br>⑨ 台词超字数<br>⑩ 运镜/表情过密<br>⑪ 同镜人数超载<br>⑫ 状态变化缺起止锚点<br>⑬ 资产编号未固定/引用错位 | **8**（规划全组） | 计划层出完，渲染前 | 回修计划，**不往下走** |
| **闸三 · 渲染闸** | ⑭ 格式/语言不匹配<br>⑮ 模型单镜上限未处理<br>⑯ 负向/BGM/字幕策略错误<br>⑰ 镜头外/心理描写进画面<br>⑱ 事实被改写/新增剧情<br>⑲ 资产图风格不统一<br>⑳ 交付缺项 | **7**（适配 + 输出两组） | 提示词/指令生成后，提交生成前 | 回修指令，**不提交** |

**5 + 8 + 7 = 20，全覆盖，无重叠。**

#### 5.4.2 为什么按这个顺序

三闸是**单向流水**，前一闸不过后面不跑：

```
闸一（5 项）──不过──▶ 停，问人
   │过
闸二（8 项）──不过──▶ 回修计划
   │过
闸三（7 项）──不过──▶ 回修指令
   │过
   ▼
  提交生成
```

**理由**：闸一缺的是「文本里没有的事实」，靠改提示词补不出来；闸二缺的是「计划算错了」，靠改措辞补不出来。**越靠前的闸，修复代价越小、能补的越少。** 把闸一的问题留到闸三才发现，等于拿提示词去编剧情——正犯底线①。

#### 5.4.3 与因果审计的关系

`分镜系统规则.md` §8.2 的因果网络审计**不是第 21 项**，它是**闸二和闸三之间的独立检查**：

| | 风险分 | 因果审计 |
|---|---|---|
| 形式 | 逐项打分 0/1/2 | 建图 + 追问 + 反事实 |
| 查什么 | 单点是否合规 | **点与点之间的因果链是否成立** |
| 触发 | 每闸各跑自己那组 | 计划层整体出完后跑一次 |
| 不过 | 该项 2 分 | 断链的话，回修计划（退到闸二） |

**为什么单列**：风险分是**逐项局部检查**，查不出「动作 A 的结果在下一镜没接上」这种**跨镜因果断裂**。因果审计补的就是这个。

#### 5.4.4 修复必须级联，不是只改一处

| 改了 | 必须重跑的检查 |
|---|---|
| 镜头时长 D | ⑥ 时间码、⑧ 动作槽、⑨ 台词字数、⑩ 密度、⑫ 锚点 |
| 台词文本 | ⑨ 字数、⑬ 资产引用；**配音作废需重跑 ASR** |
| 资产编号 | ⑬ 编号、⑲ 风格一致性；**所有引用该资产的提示词** |
| 人物设定 | ③ 主体、④ 状态变体、⑲ 风格；**该角色全部镜头** |

**判据**：改完之后，**把受影响的项全部重评一遍**，不是只重评改的那一项。

## 六、我们不做的事

明确划出去，避免越做越散。

| 不做 | 理由 |
|---|---|
| 生成图片、生成视频 | 那是模型的事。我们产出指令。 |
| 替用户编剧情 | 见底线 1 |
| 替用户做审美判断 | 风格方向要他点头，我们负责稳定执行 |
| 训模型 / 训 LoRA | 现阶段不需要；等有 50+ 成片片段再考虑 |
| 云端/本地区分 | 对用户透明，统一按 OpenAI 兼容处理 |

## 七、三条设计原则

### 7.1 引用不复制

同一个东西，**全局只有一处定义**。

人物设定在 CF 里，镜头里只写 `CH-01`。
颜色在风格母版里，每个镜头不重复写色值。

**这条不只是省 token，是防漂移。** 同一个描述写两遍，两遍一定会不一致。

### 7.2 能机械校验的不靠模型自觉

能用代码查的，绝不指望 LLM 记住。

| 能查的 | 查法 |
|---|---|
| 台词超预算 | 数字符 |
| 动作超槽 | 数动作事件 |
| 时间码不闭合 | 累加比对 |
| 枚举值非法 | 白名单 |
| 字段缺失 | schema |
| 孤立 CR / 伪行 | 字节扫描 |
| 禁写词 | 关键词匹配 |

**留给模型判断的，只剩「好不好」这种真正需要判断的东西。**

### 7.3 上下文相关，不一次抛全部

同一件事，在不同状态下给不同的信息。

- 素材清单：**只给当前分支的**，不把四张表一起塞
- 参数面板：**按「我想要 X」组织**，不是按变量名
- 错误提示：**现象 → 原因 → 一句可执行的话**

**用户不需要知道全部系统，只需要知道下一步做什么。**

## 八、自洽性检查清单

写完后自问这七条，任何一条答不上来就是设计没想清楚。

1. **这条规则，SFW 和 NSFW 都适用吗？** 如果不适用，它应该在 policy 片段里，不在 base 里。
2. **这个信息，是不是在别处已经有了？** 如果有，改成引用。
3. **这个错误，能机械检出吗？** 能就别写进 prompt 求模型自觉。
4. **改了这个，哪些下游要重算？** 列不出来说明依赖关系没理清。
5. **用户看到这个，知道下一步干什么吗？** 不知道就重写文案。
6. **这条要是没做到，会怎样？** 说不出后果的规则，删掉。
7. **这是原文的事实，还是我推断/补全的？** 标好 EVID。
