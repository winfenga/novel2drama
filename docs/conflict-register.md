## 一、🔴 致命冲突

### 冲突 1 · `task_type` 少了 `hybrid`，且推导逻辑写反

**位置**：`技术实现.md` L1018–L1047

**旧文档写的**：

```ts
type TaskType = "T2VA" | "I2VA" | "L2VA" | "FL2VA" | "Ref2VA";

function deriveTaskType(refs) {
  if (hasMedia) return "Ref2VA";
  if (hasFirst && hasLast) return "FL2VA";
  if (hasFirst) return extras.length || refs.length > 1 ? "Ref2VA" : "I2VA";
  if (hasLast)  return "L2VA";
  if (extras.length || refs.length) return "Ref2VA";
  return "T2VA";
}
```

配套说明（L1041–L1045）：
> 只有首帧 → `I2VA`，但如果还挂了别的参考图 → **升 `Ref2VA`**
> 首帧 + 尾帧 → `FL2VA`

**引擎实际**（`conditioning.py` `resolve_task_type`）：

```python
if has_refs and (has_first or has_last):
    return "hybrid"      # ← 关键帧 + 参考素材一起 → hybrid
```

**冲突点**：**逻辑方向完全相反**。

| 场景 | 旧文档 | 引擎实际 |
|---|---|---|
| 首帧 + 参考图 | → `Ref2VA`（首帧降级成普通参考） | → **`hybrid`** |
| 首帧 + 尾帧 + 参考图 | → `FL2VA`（参考图被忽略） | → **`hybrid`** |
| 只有首帧 | → `I2VA` | `i2va` |

**旧文档还漏了一个 `task_type`**：枚举里根本没有 `hybrid`。引擎有 6 个值，文档只有 5 个。

**更糟的是**：旧文档 L1003 还画了个示意图——

```
│ 推导模式：FL2VA + 1 参考   ⚠ 角色图将被忽略      │
```

**它把一个 bug 当成特性写进文档了**。引擎实际会走 `hybrid`，角色图不会被忽略。

**硬约束也没写进文档**：`conditioning.py` L335

```python
if requested not in {"ref2va", "hybrid"} and has_refs:
    raise ValueError(...)
```

**带参考素材时，点名 T2VA / I2VA 会直接报错。** 旧文档完全没提这条。

**影响**：这是主人一开始就强调的能力（"我项目之初就说了这个…就是我们的模型支持首尾帧和全能参考一起喂进去"），但旧文档把它写成了「不支持」。

### 冲突 2 · `Shot.promptVideo` 是字符串，装不下六段壳

**位置**：`技术实现.md` L195–L197

```ts
promptImage: string     // 图提示词
promptVideo: string     // 视频提示词
negativePrompt: string
```

**问题**：H3 的六段壳是**结构化**的：

```
subject_definitions:
summary:
retention_analysis:
detailed_description:
overall_soundscape:
non_diegetic_music:
```

**塞进一个 `string` 里会失去一切可校验性**：
- 没法检查 `retention_analysis` 的枚举值
- 没法检查 `<Picture N>` 编号是否连续
- 没法检查关键帧是否占了号
- 没法检查字段顺序

**还有**：三字段壳（I2VA/T2VA）和六段壳结构不同，`string` 无法表达「走哪条壳」。

**同一个 Shot 要输出多个模型时更麻烦** —— 一个 `promptVideo` 字段只能存一份。

**相关**：L730 的接口 `→ { "prompt": "...", "negative": "..." }` 同样是扁平字符串。

### 冲突 3 · 没有资产编号体系

**位置**：`技术实现.md` L229+（`Asset` 实体）

**旧文档的 `Asset`**：

```ts
Asset {
  id: string
  kind: "image" | "video" | "audio" | "portrait"
  path, url, mimeType
  parentAssetId?: string
  shotId?: string
  dialogueLineId?: string
}
```

**缺的**：

| 缺什么 | 为什么重要 |
|---|---|
| **全局编号**（`SC-01` / `CH-01` / `PR-01`） | 分镜里标记身份用编号，不重复描述 |
| **状态变体**（`SC-01-A` 白天 / `B` 黑夜） | 同场景不同时段 |
| **`@图片N` 映射** | 六段壳里 `<Picture 1>` 对应哪个资产 |
| **`role`**（身份源 / 互动角色 / 场景姿势） | Ref2VA 多图分工 |

**为什么这是致命级**：没有编号，就只能靠「每次重新描述人物外貌」来保证一致性 —— 而这正是**人物漂移的根因**。

`04_excellent-cases` 里案例 16/17 的「通用换图版」范式完全依赖 `<Subject 1/2/3>` 的职责划分，旧模型装不下。

## 二、🟠 重冲突

### 冲突 4 · 没有时长级联

**位置**：`技术实现.md` L753–L770（GUI 参数）

**旧文档的参数**：

| 参数 | 默认 |
|---|---|
| `episodeDurationSec` | 90 |
| `shotDurationRange` | [2,5] |
| `avgShotCountPerScene` | 6 |

**这是「给定范围让模型自由发挥」的思路。**

**新规则要的是「级联」**：

```
D（镜头时长）是主变量
  → 时间码  = Σ D
  → 台词上限 = floor(D × 2.5)
  → 动作槽   = min(9, round(D × 0.6))
  → 视觉节拍 = ceil(D / 4)
  → 超模型上限自动切 ceil(D / Mmax) 个子镜
```

**冲突点**：旧文档没有「改一个数要重算一切」的概念。用户改时长，其他量不会跟着变。

**更关键的**：旧文档 `shotDurationRange: [2,5]`，而 H3 的合理区间是 **5–15 秒整数**。**这个默认值本身就不对。**

## 五、根因分析

11 处冲突里，**1、2、3、4 是同一个根因**：

> **`技术实现.md` 写在我们读懂 H3 之前。**

时间线：

```
早期    技术实现.md 定稿（凭代码粗略推断）
  ↓
中期    读了 conditioning.py，发现 hybrid
  ↓
现在    读了 15 份资料，规则完整了
```

**旧文档的三处假设全部错了**：

| 假设 | 实际 |
|---|---|
| 关键帧和参考图**互斥** | **必须同时给**才走 `hybrid` |
| 提示词是**一段字符串** | 是**六段结构化字段** |
| 资产只需 **id** 就够 | 需要**全局编号 + 状态变体 + @图片映射** |

**所以不是「改几行」，是这三块要重写。**

## 七、一个观察

**四份新分册之间几乎不冲突，冲突全在「新规则 vs 旧文档」。**

新分册之间的重复倒是不少（估计 30–40%），但那是**冗余不是矛盾** —— 整理时合并去重就行，不用做选择。

**真正要主人拍板的只有 4 件**（第一批），其余都是执行层面的对齐。

**最该先动的还是那个 `deriveTaskType`** —— 它是唯一一个「文档写错了代码也跟着错」的地方，而且错的方向正好否掉了项目的核心能力。
